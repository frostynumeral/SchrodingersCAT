# Architecture

Detailed notes on each part of the code; CLAUDE.md links here.

## Models

- **`Models/`**: plain POCOs, organised as `TranslationDocument` → `TranslationFile` → `TranslationUnit` → `Segment`, with `Note`s attached at file, group or unit level. They mirror XLIFF 2.0 structure closely on purpose, so a round-trip loses nothing. Keep Core free of UI/MVVM dependencies; the UI layer will wrap these types in observable view models.
  - Files and groups hold `Items`: `TranslationUnit`s and nested `TranslationGroup`s (both derive from `TranslationItem`) in document order, so `<group>` nesting round-trips. `TranslationFile.Units`/`TranslationGroup.Units` are computed, recursive views; add units through `Items`.
  - Module and extension elements (matches, glossary, metadata, …) and `<skeleton>` are kept verbatim as detached `XElement`s in `ExtensionElements`/`Skeleton`. Foreign-namespace attributes on `<xliff>`, `<file>`, `<group>`, `<unit>` and `<note>` are kept as `ExtensionAttr`s in `ExtensionAttributes`. Core doesn't interpret either, so nothing updates them when content changes.
  - `Segment.IsIgnorable` models XLIFF `<ignorable>`. Ignorables sit in `TranslationUnit.Segments` in document order, because that order rebuilds the full `Source`/`Target` text. Use `TranslatableSegments` for anything the translator edits.
  - `Target == null` means "not translated yet". `InlineContent.Empty` means an intentionally empty translation. Keep the two distinct.
  - Segment content is `InlineContent`: an immutable, flat list of `InlineText`, `InlineCode` (`<ph>`/`<pc>`/`<sc>`/`<ec>`) and `InlineMarker` (`<mrk>`/`<sm>`/`<em>`). It is not a tree, and the two halves of a pair share an `Id`, so `<pc>` and `<sc>`/`<ec>` load into the same model and pairs can span segments. There is deliberately no implicit `string → InlineContent` conversion; use `InlineContent.FromText`. `<originalData>` lives in `TranslationUnit.OriginalData`, and foreign-namespace attributes are kept in `ExtensionAttributes`. Model records that hold lists use the internal `EquatableList<T>` so they keep value equality. The design and its rationale are in `docs/design/inline-codes.md`.
  - `SegmentState` covers only the four XLIFF states. Finer tool-specific states go in `SubState` (`prefix:value`, e.g. `cat:locked`) and are preserved verbatim.

## Checks

- **`Checks/`**: `InlineCodeHints` (built from a unit) says which source codes exist, which may not be deleted or copied, and which form non-reorderable sequences. The checker and the editor's `TargetEditModel` both use it, so they apply the same rules. `InlineCodeChecker.Check(unit)` compares a unit's target inline codes with its source codes and returns `InlineCodeIssue`s (kind, `IssueSeverity`, the segment it shows up in, the code id, and a message). It implements step 1 of `docs/design/inline-code-editing.md`:
  - **Errors:** a missing protected code; an unknown code; a copy of a non-copyable code; an unpaired half; a broken non-reorderable sequence.
  - **Warning:** a missing deletable code.
  - **Info:** reordered codes, including codes moved to another segment; a missing annotation.
  - **Scope:** it checks per unit, because pairs can span segments. Only translated, non-ignorable segments are compared with the source, but pairing covers the unit's whole target (ignorables included), as the writer does.
  - **Missing codes** are reported once per code. A half-present pair is reported as unpaired instead.
  - **Copies** are recognised by a reused `dataRef`, or by `copyOf` when the base code has no original data (XLIFF 4.7.2.4.1).
  - **Fixed-order sequences:** codes in a non-reorderable sequence of two or more codes count as non-deletable and non-copyable, whatever their attributes say (design decision 10). A lone `firstNo` code counts as reorderable.
  - It never throws on arbitrary targets, so the editor can run it on half-edited content; `InlineCodeCheckerPropertyTests` checks this.

## Checks/Qa

- **`Checks/Qa/`** (steps 1–3 of `docs/design/qa-checks.md`, which is implemented; follow its decisions): `QaChecker.Check(unit, options)` runs the segment checks (`IQaCheck`, one class each, listed in `QaChecker.Checks`) on the same segments as the code check, and returns `QaIssue`s (`QaIssueKind`, Info or Warning, never Error, the segment, a message, and an optional `Span` with `SpanInSource`). `QaOptions.Disabled` switches checks off.
  - **Text:** checks read `QaSegment`: source and target as `QaText` (plain text; a code is its `equiv` or `QaText.CodeMark`, U+FFFC, so words on either side don't join; `SpanOf` maps back to an element), and the source's `translate="no"` ranges (annotations can open in an earlier segment).
  - **Warnings:** numbers (compared by value: `.`/`,` either decimal or group separator, spaces only as group separators before three digits; a number no reading fits is compared as written; numbers in `translate="no"` text are left to that check, but an extra number in the target is still reported), target same as source (`SameAsSourceCheck.MinimumLetters`), `translate="no"` text not in the target unchanged, a repeated word (unless the source repeats it).
  - **Info:** a double space or other whitespace at either end than the source's, other end punctuation (with equivalents per script, after closing quotes and brackets), an unpaired bracket or quote (quote families only need to come in pairs; skipped if the source isn't paired).
  - **`translate="no"`:** `QaChecker` returns nothing for a unit marked `translate="no"`; one marked so by its file or a group is the caller's to leave out (`TranslationDocument.UnitsToTranslate`, which `DocumentChecker` and the app's `UnitCheck` use). "Same as source" doesn't count letters inside `translate="no"` text, so a fully protected source may be copied.
  - **Terminology** (step 2, Warning; term records since step 1 of `docs/design/termbase.md`): the check compares `TermRecord`s (source terms with synonyms, allowed `Translations`, `ForbiddenTranslations`, a `TermOrigin`: `FileGlossary` or `OfTermbase(name)`, and an optional `MarkerId`). `QaSegment.Terms` is the unit's glossary as records (`TermRecord.Of`), then what an `ITermSource` finds for the segment's source, asked lazily per segment; the source is `QaChecker.Check(unit, options, terms)`'s own argument, not part of `QaOptions` (the user's saved settings). The app passes none yet. `GlossaryReader.Read(unit)` reads the glossary module (`<gls:glossary>` in the unit's `ExtensionElements`) as `GlossaryEntry`s (term, translations, `MarkerId` from `ref="#m1"`); malformed entries are skipped, nothing is written back. A record for a term annotation checks only that annotation's segment, with its text as the term (codes in it, `equiv` text included, count for nothing, so one around codes only is no term); others any segment whose source has one of their terms. Records found for the same term (folded, whitespace collapsed) or of the same concept count as one, with all their allowed translations, so homonyms pass with either and a concept is reported once; the message names every origin, the file's glossary first. A forbidden translation never satisfies the check, and a record with no allowed translation checks nothing (the forbidden-term check is a later step). Terms and translations are found with `QaText.FindTerm` (the first of `QaText.FindAll`: `Words.FindAll` without the places whose first or last character is a code's, its `equiv` text or code mark, in the source and the target alike, so a term only in `equiv` isn't there; a code in the middle is fine): folded words matched by their beginning (`FindPhrase`), so suffixes count, with the text's runs in a script without spaces between words (CJK, Thai, …) split from the words around them; a term in such a script, or with no words (only symbols), as a folded substring that starts and ends where characters of the text do and not before a kept voicing mark (`カ` isn't in `ガ`, `をs` isn't in `をß`; a Latin `s` takes the word rule, so it is found in `ß`), its range extended over trailing combining marks; a term with punctuation (`C#`, `.NET`, `Wi-Fi`) by `FindPunctuated`: the same folded characters, only whitespace runs may differ (apostrophe variants count as one character, hyphen variants too; a code mark inside the term is skipped, one at a gap is whitespace), starting at a word beginning, its last word matching by its beginning (`e-mail` finds `e-mailt`), and a word boundary after it only if it ends in punctuation (`C#` isn't in `C#x`). The unit's glossary and source annotations are read once per unit (`QaSegment.UnitContext`, `QaSegment.OfUnit`). `QaText.SpansOf(start, length)` maps a range to every element piece it covers (codes included, cut to the text, never throws); `SpanOf` gives only the first.
  - **Document checks** (step 2): `DocumentChecker.Check(document, options)`: untranslated (Warning; skips `translate="no"` files, groups and units), inconsistent translation and inconsistent source (Info, each occurrence with `Related`), in document order. Compared with `Text/ContentKey` (the exact-match key: NFC, codes by kind), shared with the TM's `MatchScore.Normalized.KeyOf`.
  - **Words:** `Text/Words` (internal; Memory and Memory.Tests see it through `InternalsVisibleTo`) has the tokenizer, `Find`, `FindPhrase`/`PhraseAt` and `Fold`/`FoldOne` (which keep the kana voicing marks U+3099/U+309A) that the TM's matching, the concordance and the checks share. The term rule is in `Words.Terms.cs`: `FindAll(PreparedText, TermPattern)` (every place, ascending, distinct ranges, overlapping ones kept) and `FindTerm` (its first); `TermPattern.Of(term)` classifies a term once (`TermRule`: `Words`, `Punctuated`, `Folded`, `None` for blank ones) with its index `Key`, `PreparedText.Of(text)` tokenises and folds a text once (lazily; `QaText.Prepared` caches it). `TermPattern.Key` (cut by `WordRun`/`IsKeyChar`, `MaxKeyLength`) and the index's probes (`TermIndex.WordKeys`, `PlaceKeys`, which mirror `MatchAt`'s code-mark skipping and `Variant`) must agree; never change one side alone. `Fold` returns text that is folded already as the same string.
  - Tests: `QaCheckerTests` (examples per check, including what each must not report), `QaTerminologyAndDocumentTests`, `QaTermRecordTests` (origins, synonyms, homonyms, forbidden translations, the term source, terms with punctuation, codes and `equiv`, substrings on characters), `QaTextTests` (`SpansOf`), and `QaCheckerPropertyTests` (arbitrary targets never throw and spans point into their content; a target equal to its source reports at most "same as source"; the document checks never throw, and a document of copied sources has no document issues; a glossary entry whose translation is in the target reports nothing; arbitrary term records never throw; a term record whose translation is in the target reports nothing, and one whose translation isn't is reported, with terms cut only from inside a text element, away from codes; `SpansOf` covers exactly the range).

## Xliff

- **`Xliff/`**: `IXliffSerializer` is stream-based. `XliffSerializerExtensions.WriteFileAsync` saves atomically: it writes to `<path>.tmp` and then moves it over the target. `Xliff20Serializer` handles XLIFF 2.0/2.1/2.2 core. Its design rules:
  - **Fail loudly instead of losing data.** Invalid or unsupported input, such as XLIFF 1.2, invalid states, duplicate ids, unmatched `<sc>`/`<ec>` pairs, unknown elements or attributes (inline or structural), foreign elements or attributes where XLIFF allows none, stray text between elements, a file with no units or groups (or a document with no files), targets without `trgLang`, duplicate note ids within one file, group or unit, and target `order` values that repeat within a unit or exceed its number of segments and ignorables, throws `XliffFormatException`. The writer refuses everything the reader would reject before it writes a byte, so it never produces a file that won't re-read and never fails inside `XmlWriter`. A model the reader would reject throws `InvalidOperationException`: duplicate inline, segment, unit, group or file ids; unpaired halves; unknown `dataRef`s; invalid `srcDir`/`trgDir`; a unit with no non-ignorable segment; a file with no items or a document with no files; a note priority outside 1–10; undefined enum values (`SegmentState`, `NoteAppliesTo`, `InlineCodeKind`, `InlineMarkerKind`, `CanReorder`); a skeleton with neither content nor `href`; targets without `TargetLanguage`; duplicate note ids within one parent; repeated or out-of-range `TargetOrder`s; and nulls in required properties or model lists. The cross-element constraints (`FindTargetOrderProblem`, `FindDuplicateNoteId`) are shared helpers, so reader and writer can't drift apart. Model values XLIFF has no place for throw `NotSupportedException`: e.g. `Dir` on a standalone code, attributes on a closing marker, a state on an ignorable, an extension element in the XLIFF namespace, a skeleton with XLIFF children or attributes other than `href`, an extension attribute name that isn't an XML name, XML-invalid characters anywhere `<cp>` can't be used (attribute values, note text, verbatim elements), and carriage returns in comments or processing instructions, which XML can't escape. `VerifyRepresentable` checks the last of these on the finished tree. Nothing is silently dropped, because the writer regenerates the whole file from the model and anything missing from the model would be lost on save.
  - **Input is untrusted.** XLIFF files come from clients and vendors, so the reader defends against hostile files, and each attack fails with `XliffFormatException` (logged like any other read failure):
    - DTDs are prohibited (`DtdProcessing.Prohibit`, `XmlResolver = null`). XLIFF never uses one, and refusing them rules out entity expansion ("billion laughs"), external entities (file or network reads) and external DTD subsets. The predefined entities (`&amp;` etc.) and character references still work.
    - Input is limited to `MaxInputBytes` (default 256 MiB, settable with `new Xliff20Serializer { MaxInputBytes = … }`) by `LimitedReadStream`, so an endless stream stops at the limit instead of exhausting memory.
    - Elements may nest at most `MaxElementDepth` (256) deep. `DepthLimitingXmlReader` enforces this while parsing: the reading code recurses, so a file nested a few thousand deep would otherwise overflow the stack and crash the process, and building a very deep XML tree is quadratic.
    - When changing how the reader loads XML, keep all three, and keep `Xliff20UntrustedInputTests` passing. The XML mutator in the property tests also produces DTD and entity input.
  - Known limitations: only things that carry no data are dropped: namespace prefixes (the writer reuses the original ones where it can, then the conventional module prefixes, then `ns1`, `ns2`, …), comments and processing instructions outside content, `xml:space` outside content, and `xml:lang` on `<source>`/`<target>`, which must repeat `srcLang`/`trgLang`.
  - Whitespace is significant. Reading uses `LoadOptions.PreserveWhitespace`. Writing adds `xml:space="preserve"` when text has leading/trailing whitespace, runs of whitespace, or whitespace other than a plain space.
  - Reading tracks which attributes have been read (`AttributeReader`, used for structural and inline elements alike), checks unit and group ids per file (`FileContext`), and keeps per-unit id and pairing state for sources and targets separately (`InlineSide`). `<cp>` is decoded on read and re-encoded for XML-invalid characters on write. Verbatim elements are copied with `Detach`, which also declares the prefixes they use so `DeclareExtensionNamespaces` can declare the same ones on the root.
  - The writer normalises well-formed pairs to `<pc>`/`<mrk>` (`FindWellFormedPairs`). Pairs that span segments, overlap, or whose halves `<pc>` can't express fall back to `<sc>`/`<ec>` and `<sm>`/`<em>`.
  - Output is always `version="2.0"`, UTF-8 without BOM, and indented. `NewLineHandling.Entitize` writes carriage returns as `&#xD;`; otherwise XML parsers would read them back as line feeds. Content elements and verbatim elements start with an empty `XText` so XmlWriter's indentation can't inject whitespace into them.

## App

- **`SchrodingersCat.App`** (Avalonia 12, CommunityToolkit.Mvvm, compiled bindings): opens an XLIFF file, lists its translatable segments (ignorables are hidden), lets the translator edit the selected segment's target, and saves through `WriteFileAsync` (atomic, so a failed save leaves the file intact): Save (Ctrl+S) writes back to the open file, Save as (Ctrl+Shift+S) writes to a new path that then becomes the open file.
  - `ViewModels/`: `MainWindowViewModel` (open/save commands, `FilePath`, `IsDirty`, `ErrorMessage`) and `SegmentViewModel`, which wraps a Core `Segment`. `MainWindowViewModel.SelectedSegment` (bound to the list's selection) is the active segment. Each segment creates its `TargetEditModel` on first use and keeps it while the document is open, so its undo history survives leaving the segment. `ActiveEditModel` is non-null only while the segment is active and editable, so inactive rows never create one. All edits go through the model, including `TargetText`'s setter, and the model writes them to the `Segment`. View models use `[ObservableProperty]` partial properties and `[RelayCommand]`. Keep them free of Avalonia types so they stay unit-testable; dialogs (open, save as, the unsaved-changes prompt) go through `Services/IDialogService` (`AvaloniaDialogService` is the Avalonia implementation).
  - Errors: load and save failures are shown in the window's error banner instead of crashing. That covers `XliffFormatException`, `InvalidOperationException`/`NotSupportedException` from the writer, I/O and permission errors, and bad paths (`MainWindowViewModel.IsReportable`). Anything else is a bug and is deliberately not caught. A failed load keeps the current document open.
  - `Editing/TargetEditModel` (step 2 of `docs/design/inline-code-editing.md`) is one segment's target while it's edited. `TargetEditor` is the control that edits it.
    - **Tokens:** text, code halves and annotation halves.
    - **Positions:** the caret and selection count UTF-16 characters, a chip counts as one position, and a surrogate pair is never split.
    - **Operations:** each returns an `EditResult`, and a refused edit explains why.
      - `InsertText` replaces the selection.
      - `InsertCode` inserts missing halves with their source ids. A code that's already present gets a copy with a new unused id, reusing `dataRef`, or with `copyOf` when there's no `dataRef`. The copy is refused for non-copyable codes. A pair goes around the selection, or around the caret.
      - `InsertNextMissingCode` follows source order.
      - `Delete` never removes a protected code. It removes only one half of a pair, and deleting a selection keeps protected codes.
      - `CopySource` leaves out code and annotation halves already in another segment's target.
      - `Paste(content, fromUnit)` replaces the selection. Codes and annotations come along only from the same unit (by reference): a code missing from the target is inserted as it is (so cut and paste moves it), a code already there becomes a copy if it may be copied (whole codes only), annotations only whole and only if not in the target yet; the rest is left out with a note. From another unit or app, only the text. `SelectedContent()` is the selection for the clipboard.
      - `Undo`/`Redo`: typing is grouped by word, and code edits are separate steps.
    - **Target writes:** every applied edit writes `Segment.Target` (an empty result means `null`, unless the target was intentionally empty). The model never changes `Segment.State`, not even on undo.
    - **Scope:** ignorables can't be edited.
  - Chips (step 4 of `docs/design/inline-code-editing.md`): the source column, and the targets of the rows not being edited, show codes as chips. `ContentRuns` (view model, no Avalonia types) turns `InlineContent` into `TextRun`s and `ChipRun`s.
    - **Label:** `disp`, then a name from `subType`/`type` (`xlf:b` → `b`, `xlf:lb` → `↵`), then the id. `ChipRun.Text` adds the pairing bracket (`⟨b`, `b⟩`).
    - **Tooltip:** the native code from `OriginalData`, `equiv`, and the `InlineCodeHints` in words.
    - **Protected:** the chip shows a lock. Annotations aren't chips; they style the text they cover (term, comment, `translate="no"`), and an annotation opened in an earlier segment of the unit still styles the next one.
    - `Controls/InlineContentBlock` (a `SelectableTextBlock`) renders the runs with `InlineUIContainer`s. Chips are `Border.chip` with the classes `opening`/`closing`/`standalone`, `protected` and `problem`, styled in `Styles/ContentStyles.axaml` (included by `App.axaml`, so dialogs draw chips too). While hidden (the active row's read-only target), it defers rebuilding until shown again: Avalonia renders a hidden `TextBlock` whose inlines changed, measures the new chips during that render, and throws "Visual was invalidated during the render pass". `InlineFormatter`'s `⟨1⟩…⟨/1⟩` text stays for plain-text uses (`SourceText`).
  - `Controls/TargetEditor` (step 5) is the editor for the active segment's target, built on AvaloniaEdit as the spike was.
    - **Encoding:** each chip is one U+FFFC character in the document, drawn by a `VisualLineElementGenerator` with the same `Chips` factory as the read-only views. Which offsets are chips is tracked separately, so a literal U+FFFC in a translation stays text.
    - **No direct edits:** a read-only section provider blocks AvaloniaEdit's own edits. Typing (`TextEntering`), Backspace/Delete, Enter, Ctrl+Z/Ctrl+Y, Ctrl+X and Ctrl+V go to the model, and the control redraws on the model's `Changed` event.
    - **Status:** the model's message for each edit (a refusal or a note) goes to the two-way `Status` property, bound to `SegmentViewModel.EditStatus`. The window's status line shows the selected segment's message.
    - **Caret:** the editor's caret and selection are pushed to the model on every move, so edits from outside the editor (a source chip click) land at the caret. After such an edit the editor takes the keyboard back.
    - **Keys (step 7):** F9 inserts the next missing code; Ctrl+Shift+F9 opens the code picker (`CodePicker` popup, type-ahead over `ViewModels/CodeChoice`, Up/Down, Enter, Escape).
    - **Clipboard:** `Controls/SegmentClipboard`. Copy (Ctrl+C), cut (Ctrl+X, Shift+Delete) and the source column's Ctrl+C (`InlineContentBlock.ClipboardUnit`, sliced with `ContentRuns.Slice`) put plain text with `⟨1⟩` placeholders on the clipboard, plus a token in an app-specific format that points at the copied content and its unit, kept in the process (weakly). Paste (Ctrl+V, Shift+Insert) uses that content if the token matches, else the clipboard's text without chip characters, and goes through `TargetEditModel.Paste`.
    - The other rows show their targets read-only with `InlineContentBlock`, in the same `Border.targetFrame` (`editing` when active).
  - Integration (step 6):
    - **Editable:** every translatable segment is editable, codes or not.
    - **Checks:** `ViewModels/UnitCheck` holds one unit's `InlineCodeChecker` results (`CodeIssues`), `InlineCodeHints` and, since step 3 of `docs/design/qa-checks.md`, `QaChecker` results (`QaIssues`, with `MainWindowViewModel.QaOptions`; none for units `TranslationDocument.UnitsToTranslate` leaves out). It is shared by the unit's rows and re-runs after every edit, so an edit in one segment updates the others (pairs can span segments). Each `SegmentViewModel` exposes the issues of its segment as `SegmentIssue`s (`Code` or `Qa`; code issues first): `Issues`, `HasErrors` (only code issues can be errors, so the save prompt and the TM store still depend on codes alone), `HasWarnings`, `IssueSummary`, shown as a `Border.issueBadge` (count, coloured by the worst severity, the messages in the tooltip). Untranslated segments never get a badge.
    - **Outlines:** errors and warnings mark the chips involved (`ChipRun.HasProblem`, class `problem`): missing codes in the source, the other problems in the target (`TargetProblemCodes`, also passed to `TargetEditor.ProblemCodes`). Info issues mark nothing.
    - **Source chips:** clicking one in the active row runs `InsertCodeCommand` (`InlineContentBlock.ChipCommand`), which inserts the code at the editor's caret.
  - The QA tab (step 4 of `docs/design/qa-checks.md`): `PaneTab` 2, `ViewModels/QaReportViewModel` (`MainWindowViewModel.Qa`).
    - **Report:** F8 (tunnelling handler, `Qa.RunCommand`) lists every row's `AllIssues` (code issues as the first group, `QaChecks.CodesLabel`) and `DocumentChecker`'s issues, as `QaReportHeader`/`QaReportEntry` rows grouped by check (`QaChecks.All` order), segments in document order. Entries keep their state until F8 runs again: `IsFixed` (the issue is gone; for document checks, translated or target changed; identical issues in one segment count one by one, `QaReportEntry.UpdateAll`) and `IsDismissed` follow the segment's `PropertyChanged`. F8 gives the list the keyboard (its first entry); headings (`QaReportRow.IsEntry` false) aren't focusable or clickable, so Up/Down pass over them. A click on an entry or Enter (`QaList`, MainWindow.axaml.cs; Enter with `handledEventsToo`, as the list item handles it first) runs `OpenCommand`, which selects the segment and raises `EditorRequested` (the window focuses the editor at Loaded priority).
    - **Dismissing:** `SegmentViewModel.SetDismissed`/`DismissCommand` (the badge's context menu) and `Qa.ToggleDismissedCommand` (the entry's Dismiss/Restore button, labels from styles). Only quality issues (`SegmentIssue.CanDismiss`; the badge's menu lists `DismissableIssues`). Kept by check and message, a document check's by check alone (its message counts other segments, which can change while this target stays). Dismissed issues leave `Issues` (badge, `HasWarnings`, Ctrl+Shift+Down) but stay in `AllIssues`; any target change drops them.
    - **Settings:** `Qa.SettingsCommand` → `IDialogService.EditQaSettingsAsync` (`Views/QaSettingsDialog`, `QaSettingsViewModel`, one `QaCheckChoice` per `QaChecks.All`). `MainWindowViewModel.UseQaOptions` re-runs every `UnitCheck`, the report if it ran (cleared first, so it doesn't follow every re-check), and saves `AppSettings.DisabledQaChecks` (names; read at startup by `QaOptionsFrom`). `SaveSettings` changes one setting and keeps the others (the TM path too).
    - Tests: `QaReportTests` (view model, and the real window and settings dialog).
  - Keyboard workflow (step 7, design section 4): Ctrl+Enter confirms the segment (Initial → Translated; refused without a translation) and moves on, Ctrl+Down/Ctrl+Up move between segments, Ctrl+Shift+Down goes to the next segment with errors or warnings (code or quality), and Ctrl+Insert copies the source, asking first (`IDialogService.ConfirmAsync`, `ConfirmDialog`) if there is a translation. They are `MainWindowViewModel` commands, mapped in a tunnelling key handler in `MainWindow.axaml.cs`, because AvaloniaEdit would take these keys before window key bindings see them.
  - Editing rules: clearing a target sets it to `null` (not translated). The first translation moves a segment from `Initial` to `Translated` (in `SegmentViewModel`, on the model's `Changed` event); nothing moves it back, not even undo.
  - Matches pane (step 4 of `docs/design/translation-memory.md`): the app references `SchrodingersCat.Memory`.
    - **Sources:** `MainWindowViewModel.Matches` holds the selected segment's matches (`MatchViewModel`), at most nine, best first: the file's (`SegmentViewModel.FileMatches`, from `XliffMatches`; those whose `ref` points to the segment, or anywhere in a unit with only that segment to translate) and the open TM's (`TranslationMemory`, an `OpenTranslationMemory`).
    - **Lookup:** `OpenTranslationMemory.LookupAsync` runs in the TM's queue (below). A new selection cancels a lookup that hasn't started and drops the result of one that has. `MatchLookup` (internal) is the latest lookup, for tests to await. `TmFormatException`, `DbException` and `IOException` go to the error banner; the file's matches stay. Context for 101% is the plain text of the neighbouring segments in the list (`Neighbours`, shared with storing).
    - **Display:** the match's source with `SourceDiff` (Memory) against the current source, as runs with a `Difference` (`ContentRuns.BuildDiff`): removed text struck through, added text highlighted, chips with `removed`/`added`. The match's own codes get plain chips (their ids mean nothing in this unit). The target is shown as it would be inserted: `CodeTransfer` onto the current source.
    - **Inserting:** Ctrl+1 … Ctrl+9 (`InsertMatchCommand`, in the tunnelling key handler) or the row's non-focusable button replace the target via `TargetEditModel.ReplaceTarget` (the rules of `CopySource`, which now calls it), as one undoable edit. The status line says which match went in and whether codes are missing.
  - Translation memory (step 5 of `docs/design/translation-memory.md`):
    - **The open TM:** `Services/OpenTranslationMemory` owns one `ITranslationMemory` (`Open`/`Create` wrap `SqliteTranslationMemory`) and runs every operation (lookup, store, import, export) in a FIFO queue on the thread pool: each is a `ContinueWith` of the previous, never passed the token (a cancelled continuation would let the next one start early), so failures don't stop the queue. Only synchronous work goes in the queue (TMX is parsed and written outside it). `DisposeAsync` waits for the queue, then closes the TM; queuing after that throws `ObjectDisposedException`. `MainWindowViewModel.UseTranslationMemoryAsync` swaps TMs (the setter is private) and disposes the old one.

## Memory

- **`SchrodingersCat.Memory`** (step 1 of `docs/design/translation-memory.md`; follow its decisions): a separate project so Core keeps no storage dependencies.
  - `TmEntry` (source and target `InlineContent`, neighbouring sources for context, document, date, user) and `TmMatch` (entry and score).
  - `MatchScore`: sources compared normalised (NFC, whitespace between words ignored, annotations ignored, codes as their kind only); word-level edit distance as a percentage of the longer source, punctuation marks as words, two numbers as the same word; minus 1 per differing number and 2 per differing code. Only sources equal before normalisation score 100, case or whitespace alone 99. Symmetric. Text `Normalize` rejects (lone surrogates, U+FFFF from `<cp>`) is compared as it is.
  - `InMemoryTranslationMemory`: `Add` replaces a pair equal ignoring code ids and keeps other translations of the same source (decision 4); `Lookup` scores every entry, 101 for an exact match with the same neighbours (needs at least one), threshold 70, at most 5, best then newest first.
  - `CodeTransfer`: maps a match's codes onto the current source's (in order per kind; closing halves follow their opening), leaving out codes that don't pair and annotations; `AllCodesPlaced` says whether the translator still has codes to insert.
  - `ITranslationMemory` (`Count`, `Add`, `AddRange`, `Remove` and `Replace` by pair, `Entries`, `Lookup`, and the maintenance operations below) has two implementations; `Ranking` holds the lookup rules they share (scoring, context, threshold, order), so they can't drift apart.
  - `SqliteTranslationMemory` (step 2): a `*.sctm` SQLite file (`Microsoft.Data.Sqlite`) per TM and language pair, `Create`/`Open`/`Add`/`AddRange`/`Lookup`. Content and plain strings are stored with `TmContentFormat` (internal, versioned binary, strings as raw UTF-16; `Read` validates and throws only `TmFormatException`). Fuzzy candidates come from a word-bigram index (`postings`, `features` with document frequencies): the query's bigrams rarest first within `PostingBudget` rows, the `CandidateCount` entries sharing most, then `Ranking`. The spike's numbers and the reasoning are in step 2 of the design.
  - Maintenance (step 1 of `docs/design/tm-maintenance.md`; follow its decisions):
    - **Ids:** `TmEntryId` (the SQLite row id; a counter in memory) on `TmMatch.EntryId`, `ConcordanceHit.EntryId` (null for the file's matches and for TMs without ids) and `StoredEntry`. Ids increase in the order stored and are never reused: SQLite keeps the highest id deleted in `meta` (`last_deleted_id`) and a new entry gets the next after both.
    - **Operations:** `Find`, `Update(id, target, changed, changedBy)` (keeps source, document and context; merging into an equal stored pair removes the other, the edited one keeps its id: `UpdateResult.Merged`), `Delete(ids)`, `Browse(filter, after, pageSize)` (newest first by id, keyset paging, with the total), `DeleteMatching(filter)`, `Documents`, `Users`, `Compact`. Stale ids give `NotFound`/0, never an exception.
    - **Filters:** `EntryFilter` (text with the concordance's rules, document, user, `ChangedFrom`/`ChangedBefore`, `SeveralTranslations` by `MatchScore.Normalized.KeyOf`); the rules are shared in `Maintenance` (internal). SQLite checks dates, document and user in SQL (a string is always stored as the same bytes) and decodes only the column a content condition needs.
    - **Deleting:** below `BulkDeleteShare` (2%) of the TM one by one through the bigrams; from there in one pass over `postings`, then `features` recounted. `Compact` runs `VACUUM` once more than a quarter of the entries were deleted since the last one (counted in `meta`, `deleted_since_compact`), because scattered deletes don't free pages. The measurements are in step 1 of the design.
  - `Tmx` (step 3): TMX 1.4b `ReadAsync`/`WriteAsync`. Pairs within a segment are `<bpt>`/`<ept>` (`i` never reused within a segment), lone halves `<it>`, standalone codes `<ph>`; `x` ties source and target codes and becomes the code id on import. Native code data isn't kept. Import keeps the XLIFF reader's defences (no DTD, `LimitedReadStream`, `DepthLimitingXmlReader`, reused from Core through `InternalsVisibleTo`, with an error factory so they throw `TmFormatException`), skips and reports units it can't use, and takes regional variants of the TM's languages (decision 3). Export skips and reports entries whose text XML can't hold.
  - `Concordance` (follow-up, see the design doc's "Concordance"): `ConcordanceQuery.Parse` and `Concordance.Search(memory, query, side, maxHits)` → the best hits (`ConcordanceHit` with `HighlightPart`s) and the total. Words as `MatchScore` tokenizes them, punctuation ignored, folded per character through a table (`Fold`, now in Core's `Text/Words` with the tokenizer, shared with the QA checks: lower case, no accents, ł/ø/đ/æ/œ/ß spelled out; never fails), each query word matching a word's beginning, consecutively. Ranked whole-word hits, shorter, newer, then stored order (a total order: ties are never dropped). It scans: `SqliteTranslationMemory.ScanSide`/`Load` (internal) read only the searched column and load the kept hits; other TMs go through `Entries()`. Checks cancellation every `CheckEvery` entries.
  - `TmLanguages` (step 5): whether a TM serves a document's languages (decision 3), shared with TMX import's language rule.
  - `SourceDiff` (step 4): a match's source against the current source, as `DiffPart`s (`Same`, `Removed` from the match, `Added` from the current source), on the words `MatchScore` tokenizes, but case- and number-sensitive; codes by kind, annotations left out, whitespace never a difference. Common prefix and suffix are trimmed, the middle is an LCS up to `MaxCells`, beyond that removed then added.
  - `XliffMatches` (step 3): reads `<mtc:matches>` from a unit's `ExtensionElements` as `XliffMatch` (segment id from `ref`, `TmMatch` with `Origin`, score from `matchQuality` or `similarity`), with Core's own inline reader (`Xliff20Serializer.ReadStandaloneContent`, internal) and the match's `<originalData>`. A match that breaks the rules is left out; nothing is ever written back.
  - TM files are untrusted like XLIFF: `Open` requires exactly the expected tables and indexes (no triggers or views of the file's own; only an index whose name matches `GLOB 'sqlite_autoindex_*'` and has no SQL is SQLite's own, as `LIKE`'s `_` would match any character), the format and version in `meta`, and sets `trusted_schema=OFF`; anything else, and damaged entries found later, throw `TmFormatException`. Connections don't pool, so disposing closes the file.
  - Termbase entries and index (step 2 of `docs/design/termbase.md`; follow its section 2):
    - **Entries:** `TermEntry` (source terms, at least one, and target terms as `Term`s with a `TermStatus`, notes, date, user; lists copied into `EquatableList`, nulls, an empty source and undefined statuses throw, blank terms allowed and never found), `TermEntryId`, `StoredTermEntry`. `ToRecord(origin)` is the check's `TermRecord`: every source term (forbidden synonyms too), preferred first; non-forbidden targets as translations, forbidden ones as `ForbiddenTranslations`.
    - **`TermIndex`:** immutable snapshots (`ImmutableSortedDictionary` by id, two `ImmutableDictionary`s of key hash → candidates, one for word terms, one for the rest); `With`, `WithRange` (one snapshot for many, as an import), `Without` (the same instance for a stale id), `WithoutRange`, `Of` share what's unchanged, so lookups need no lock. A builder copies a key's bucket once per batch, so many terms under one key stay linear (`ManyTermsUnderOneKey_…`); `Of`/`WithRange` classify chunks of entries on other threads while the next chunk is read, and throw what reading threw (unwrapped). Every source term is filed under its `TermPattern.Key`, hashed (FNV-1a, 64 bits): word terms by their first folded word run, punctuated terms by their folded characters up to the first space (`c#`, `.net`, `wi-fi`, apostrophes and hyphens as one), no-space and symbol-only terms by their first folded character; all cut at `Words.MaxKeyLength` (16). `Find(QaText)` probes each word's run beginnings, and each place's character and (where a word may begin) its character beginnings up to whitespace, code marks skipped; a bit per key hash (`KeyFilter`, never cleared) skips most lookups, and a phrase's second word's first character is compared before `Words.PhraseAt`. Candidates are confirmed by the rule (`Words.PhraseAt`, `FoldedAt`, `PunctuatedAt`), so hits never start or end in a code. `TermHit`: id, entry, `MatchedTerms` (before collapsing), `Occurrences` (`TermOccurrence`: term index, start, length; by start, longer first, one per range under the lowest term); hits by first occurrence (longer first), then id. `Scan` (internal) tries every term: what `Find` must equal. `ToTermSource(name, previous)` is the check's `ITermSource` over one snapshot; each entry's `TermRecord` is made once per source and kept by it, because a record keeps what the terminology check works out from it (`TermRecord.Checked`: its terms and allowed translations trimmed, keyed and classified; a record copies its lists). The index keeps no records: one costs about 800 bytes, and kept for every entry ever found they grew past the memory budget (step 3's "Memory after use"). So keep a source per document, not per session; after a write, pass the document's previous source as `previous` and the new one takes over its records (by the entry's place in the index, so a changed entry gets a new one).
    - **Step 6:** `TermProbe.Of(entry)` (one entry's terms classified once): `IsIn(QaText)` (stops at the first place) and `Find(QaText, id)` (what a one-entry index finds; `TermIndex.HitOf`, the `Scan` loop for one entry). `TermIndex.Merge(hits, without, with)` (cached hits after a write, in `Find`'s order, `ByFirstPlace`). `TermIndex.WithSourceTerm(term)` (entries with a source term of the same `Words.SameTermKey`, by id; the index's candidates in the term's own text, or a scan of every entry for a term with a literal U+FFFC or one the rule doesn't find whole in its own text). `TermEntry.SameTerm(a, b)`. `Words.SameTermKey` (Core, internal) is the check's "same term" key, moved from `SegmentChecks`. Tests: `TermProbeTests`, and in `TermIndexPropertyTests` a probe equals a one-entry index, merged hits equal a find after random writes, `WithSourceTerm` equals a scan.
    - Tests: `TermIndexTests` (each rule, every occurrence, codes and `equiv`, snapshots, entries, the term source with `QaChecker`) and `TermIndexPropertyTests` over `TermGen` (pieces with suffixes, folds, no-space scripts, punctuation, codes inside words) and `XliffGen` sources: the index equals the scan, every hit is a place the rule finds, `FindTerm` is the first of `FindAll`, `Fold` is `FoldOne` per character (folded text comes back as the same instance), snapshots equal a rebuild, the term source agrees with the check, lookups never throw, and `Generators_CoverWhatThePropertiesClaim`.
  - Termbase storage (step 3 of `docs/design/termbase.md`; its section 3 and the step's decision):
    - **`ITermbase`:** `SourceLanguage`, `TargetLanguage`, `Index` (the current `TermIndex` snapshot; every read goes through it), `Add`, `AddRange` (one transaction, one snapshot, ids ascending in input order), `Update` (the whole entry under its id; false for a stale id), `Delete` (unknown and repeated ids skipped; returns how many), `Compact`. Every write either commits and then publishes a new snapshot, or throws and leaves the file and `Index` as they were. Nothing is merged: equal entries are homonyms. `Changed` is stored as UTC. Writes run one at a time; `Index` can be read from any thread.
    - **`InMemoryTermbase`:** the reference the property test compares against; same id rule (the next id is one more than the highest given or deleted), same normalising and argument checks (`SqliteTermbase.Normalized`, shared).
    - **`SqliteTermbase`** (`*.sctb`, laid out like `SqliteTranslationMemory`): `Create` (refuses an existing file, deletes what it made on failure), `Open(path, cancellationToken)` checks the file, then loads every entry into `Index` before it returns (about 1.7 s for 200,000; call it on a background thread; cancelling closes the file). Tables `meta`, `entries`, `terms` are `STRICT`; `terms` is `WITHOUT ROWID`, keyed (entry, side, position), so `Load` merges two ordered readers, reading each row in one `GetValues`. Strings are raw UTF-16 BLOBs (`TermbaseText`; `NULL` is null, an empty BLOB is ""), `changed` UTC ticks, `side` 0/1, `status` `(int)TermStatus` (pinned by a test). Ids increase and are never reused (`last_deleted_id` in `meta`; `AddRange` checks the whole batch's ids stay within `long` before it writes, as a wrapped id would make the file unopenable); `Compact` runs `VACUUM` once more than a quarter was deleted (`deleted_since_compact`), the TM's rule. Prepared commands are reused per write.
    - **Untrusted files:** `Open` compares `sqlite_schema` with the three tables' exact SQL text (so no triggers, views, indexes, `sqlite_stat1`, extra tables, `ALTER TABLE`d or non-`STRICT` tables), requires the four meta keys and allows only the two counters besides (digits only; keys and values stored as text, as the writes read them), sets `trusted_schema=OFF`, doesn't pool, and checks every loaded value (ids ascending, no orphan terms, sides and contiguous positions, defined statuses, even BLOB lengths, ticks in range, a source term per entry). Anything else throws `TermbaseFormatException` (its own type, also for step 4's TBX/CSV); the file is closed first, so it can be deleted at once. A failed write (e.g. `SqliteException` busy) passes through unchanged.
    - Tests: `SqliteTermbaseTests` (round trip with lone surrogates, `\0`, U+FFFF and "" versus null; pinned numbers; `Create`/`Open` errors; cancelling, also during loading through `Open`'s internal `checkpoint`; ids at the end of `long`; meta values that aren't text; a theory of files that aren't ours and one of damaged entries, each refused with `TermbaseFormatException` and closed: `AssertClosed` looks for the file among the process's open files in `/proc/self/fd` on Linux, where deleting an open file succeeds, and opens it unshared elsewhere), `TermbaseTests` (abstract, run by `InMemoryTermbaseTests` and `SqliteTermbaseMaintenanceTests`: ids, snapshots, stale ids, nulls, UTC; reopening, `Compact`, a failed write), `TermbaseTextTests`, and `TermbasePropertyTests`: random scripts of adds, imports, updates (stale ids too), deletes, reopenings and compactions keep the file and the in-memory termbase equal (and the snapshots equal a rebuild, the file without orphans or gaps), and damaged files (bytes, truncation, values) either open to exactly the file's rows, read apart from `Load` (positive ids, each side's positions from 0, no orphan terms), or fail only with `TermbaseFormatException`, and are closed either way.

    - **Results:** `TermImport` (entries for one `ITermbase.AddRange`, never `Add` in a loop; `Skipped`, `Notices`, `Dropped` counted by data category) and `TermExport` (`Written`, `Skipped`, `Incomplete`, CSV only). Status names (section 4's table, CSV's words) live in `TermStatusNames` (internal).
    - **`Tbx`** (`Tbx.cs`, `Tbx.Read.cs`, `Tbx.Write.cs`): `ReadAsync(input, source, target)` reads TBX 2 (`martif`: `tig`, `ntig`/`termGrp`) and TBX 3 (`tbx` in `urn:iso:std:iso:30042:ed-2`: `conceptEntry`/`langSec`/`termSec`), DCA and DCT whatever `style` says. DCT is matched by namespace URI (`MinNamespace`, `BasicNamespace`), never by prefix.
      - What it keeps: terms (`.Value`, untrimmed), the status (`administrativeStatus` before `normativeAuthorization`; an unknown value gives Unspecified and a Notice), term notes, and the concept's notes and definitions joined with `\n` (the two languages' ones prefixed `tag: `). The date and user come from the modification `transacGrp` with the latest readable date at any level (concept, language, term), else the origination with the latest one; a modification without a readable date still wins over a dated origination (the entry keeps its user, no date); the date is UTC, and an unreadable date gives a Notice only when it leaves the entry without one.

## Logging

- **Logging**: Core depends only on `Microsoft.Extensions.Logging.Abstractions`; the app picks the backend. Classes take an optional `ILogger<T>` in the constructor and fall back to `NullLogger<T>.Instance`, so they work without one. Use `[LoggerMessage]` source-generated methods (the class must be `partial`), because plain `LogError(...)` calls fail the build with CA1848/CA2254. Wrap arguments that cost something to compute in `_logger.IsEnabled(...)` and compute them in a local inside the guard; CA1873 still fires if the expression is passed inline. `Xliff20Serializer` logs at the public `ReadAsync`/`WriteAsync` boundary: Error on failure, attaching the exception and then re-throwing it, and Debug with a summary on success. Tests use `FakeLogger<T>` from `Microsoft.Extensions.Diagnostics.Testing`.
  - **The app's log file:** `Program.Main` logs to `Services/RollingFileLoggerProvider`: `SchrodingersCAT/logs/schrodingerscat.log` in the *local* application data folder (logs don't roam; `DoNotVerify`, because a folder that doesn't exist yet would give `""` and a log in the working directory), rotated at 1 MiB into `schrodingerscat.1.log` … (5 files kept). Each line (time, level, process id, category, message, then the exception) is appended with the file opened and closed again under an exclusive `schrodingerscat.log.lock`, so the last lines before a crash survive, a viewer can read the file, and several app instances neither overwrite each other's lines nor rotate together (`FileMode.Append` alone seeks to the end only once). Rotation moves the current file aside (`.rotating`) first: if that fails nothing moves and the line goes in past the limit; if moving the older files up fails, the current file goes back; a file left aside (a crash mid-rotation) is rotated before anything else, never overwritten. The lock is waited for (up to 1 s) only when another process holds it (`IsHeldElsewhere`); other failures write without it at once. Logging never throws, not even for an exception whose `ToString` throws. `AppDomain.UnhandledException` logs crashes as Critical (exceptions escaping the UI loop come out of `StartWithClassicDesktopLifetime`), unobserved task exceptions as Error (only when the GC finalizes the task, so work an event handler can't await goes through `Services/Background.Forget()`, which logs its failure as Error without crashing; don't write `_ = SomethingAsync()`), and Avalonia's own warnings and errors go in through `AvaloniaLogSink` (`Logger.Sink`, set after `BuildAvaloniaApp`'s `LogToTrace`; category `Avalonia.<area>`, at their own level). The level is Information unless `SCHRODINGERSCAT_LOG_LEVEL` says otherwise (e.g. `Debug`). Classes get their loggers from `App.Loggers` (`NullLoggerFactory` in tests, which never run `Main`). Help → Open log folder (`OpenLogFolderCommand`, `IDialogService.OpenFolderAsync`) shows `MainWindowViewModel.LogFolder` in the file manager so users can send the logs in; `Notice` always gives the path, because on Linux opening counts as done once `xdg-open` has started, even if it then fails.

## Property-based tests

`Xliff20PropertyTests` uses [CsCheck](https://github.com/AnthonyLloyd/CsCheck) to generate random documents. Each property runs 100 iterations in a normal `dotnet test`. The properties:

- **Valid documents** (from `XliffGen` in `tests/SchrodingersCat.TestSupport`) round-trip losslessly: write→read gives back the same model, compared property by property via reflection in `ModelComparer`, so new model properties are covered automatically. Write→read→write gives the same XML.
- **Mutated models** (`ModelMutator`): the writer throws only `InvalidOperationException`/`NotSupportedException`, or writes a file that reads back and writes identically.
- **Mutated XML** (`XmlMutator`): structural, text and byte-level damage. The reader throws only `XliffFormatException`, or returns a model that writes, reads and writes identically.
- **Coverage:** `Generators_CoverWhatThePropertiesClaim` checks that a sample really contains the features the generators claim to produce (nested groups, spanning pairs, `<pc>` and `<sc>`/`<ec>`, `<cp>`, extensions, …), and that both mutation properties exercise both their accept and reject branches.
